# Feature Specification: RAG-ответы по документу КЦ (v3)

**Feature Branch**: `001-v3-langgraph-rag`

**Created**: 2026-11-21

**Status**: Draft

**Input**: User description: "Переписать бэкенд v3 на LangGraph шаг за шагом: безупречные ответы строго по контексту /backend/data, ничего лишнего"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Ответ по документу (Priority: P1)

Пользователь задаёт вопрос о содержании документа КЦ. Система находит относящиеся к вопросу фрагменты
документа и отвечает, опираясь только на них, указывая, из каких фрагментов взят ответ.

**Why this priority**: это единственная ценность сервиса; без неё остальное не имеет смысла.

**Independent Test**: подать на вход вопрос, ответ на который прямо есть в документе; ответ должен
содержать факт из документа и ссылку на фрагмент-источник.

**Acceptance Scenarios**:

1. **Given** документ загружен и проиндексирован, **When** пользователь спрашивает «<вопрос по документу>», **Then** ответ содержит факт из документа и ссылки на использованные фрагменты.
2. **Given** вопрос допускает несколько мест документа, **When** пользователь его задаёт, **Then** ответ объединяет факты из найденных фрагментов без противоречий.

---

### User Story 2 - Честный отказ (Priority: P1)

Пользователь задаёт вопрос, ответа на который в документе нет. Система отвечает «в документе этого нет»
и не выдумывает факты.

**Why this priority**: без отказа сервис бесполезен и опасен — галлюцинации хуже отсутствия ответа.

**Independent Test**: подать вопрос вне тематики документа; ответ должен быть отказом без новых фактов.

**Acceptance Scenarios**:

1. **Given** документ не содержит сведений, **When** пользователь спрашивает о них, **Then** система отвечает отказом в стандартной формулировке и не добавляет утверждений, которых нет в документе.
2. **Given** вопрос частично покрыт документом, **When** пользователь его задаёт, **Then** система отвечает только по покрытой части и явно указывает, чего в документе нет.

---

### User Story 3 - Прозрачность каждого этапа (Priority: P2)

Пользователь (разработчик) хочет видеть, что произошло на каждом этапе обработки: какие фрагменты
получились при разбиении документа, что нашёл поиск, какой текст ушёл модели и что она вернула.

**Why this priority**: цель работы — понимание пайплайна и управляемая отладка качества.

**Independent Test**: выполнить один запрос и получить по нему сохранённый набор артефактов этапов.

**Acceptance Scenarios**:

1. **Given** документ разбит на фрагменты, **When** разбиение выполнено, **Then** все фрагменты доступны для просмотра с их порядком и границами.
2. **Given** выполнен запрос, **When** он обработан, **Then** сохранены найденные фрагменты, итоговый запрос к модели и ответ модели.

---

### Edge Cases

- Вопрос пустой или состоит из пробелов — система отвечает ошибкой валидации, не вызывая модель.
- Документ отсутствует или нечитаем — сервис не стартует в рабочем режиме и сообщает причину.
- Вопрос длиннее разумного предела — система отвечает ошибкой валидации.
- Ни один фрагмент не найден — система отвечает отказом, модель не выдумывает ответ.
- Модель недоступна — система возвращает ошибку без подмены ответа.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать текстовый вопрос пользователя и возвращать текстовый ответ.
- **FR-002**: Система MUST строить поисковый индекс по всем документам каталога `/backend/data` при старте.
- **FR-003**: Система MUST разбивать документ на фрагменты, сохраняя порядок и возможность указать источник.
- **FR-004**: Система MUST находить фрагменты, релевантные вопросу, и формировать ответ только на их основе.
- **FR-005**: Система MUST возвращать вместе с ответом перечень использованных фрагментов-источников.
- **FR-006**: Система MUST отказываться от ответа, если в найденных фрагментах нет оснований для ответа.
- **FR-007**: Система MUST не добавлять в ответ факты, отсутствующие в документе.
- **FR-008**: Система MUST сохранять артефакты этапов: фрагменты документа, результат поиска, запрос к модели, ответ модели.
- **FR-009**: Система MUST отклонять пустой вопрос и вопрос сверх установленного предела длины с ошибкой валидации.
- **FR-010**: Система MUST сохранять HTTP-контракт чата, используемый текущим фронтендом (запрос, ответ, стриминг).
- **FR-011**: Система MUST оставаться работоспособной при повторных запросах без перестроения индекса, если документы не изменились.

### Key Entities

- **Документ**: файл из `/backend/data`; атрибуты — имя, содержимое, признак изменения.
- **Фрагмент**: непрерывная часть документа; атрибуты — текст, номер по порядку, ссылка на документ и позицию.
- **Запрос**: вопрос пользователя; атрибуты — текст, время.
- **Ответ**: текст ответа или отказ; атрибуты — использованные фрагменты, признак отказа.
- **Артефакт этапа**: сохранённый вход и выход этапа обработки.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На наборе контрольных вопросов по документу доля ответов, подтверждаемых документом (faithfulness), не ниже 0.845 и стремится к 0.90.
- **SC-002**: На наборе вопросов вне документа 100 % ответов — отказ без выдуманных фактов.
- **SC-003**: 100 % ответов содержат хотя бы один фрагмент-источник либо являются отказом.
- **SC-004**: Для любого выполненного запроса доступны артефакты всех этапов обработки.
- **SC-005**: Повторный запуск при неизменных документах не перестраивает индекс и происходит заметно быстрее первого.

## Assumptions

- Источник знаний — только файлы в `/backend/data` (сейчас один документ `КЦ.docx`); внешние источники не используются.
- Язык вопросов и документа — русский.
- Диалог без памяти между сообщениями: каждый вопрос обрабатывается независимо (уточняющие вопросы вне области этой версии).
- Small talk и защита от нежелательного ввода вне области этой версии.
- Фронтенд не изменяется; сервис подстраивается под его текущий контракт.
- Старые каталоги `backend/`, `frontend/`, `eval/` остаются без изменений; новый код — в `backend/src/v3/`.
